Рабочие заметки для агента. Читать перед любой правкой этого проекта.

## Что это

Прошивка ESP32 (DOIT DevKit V1, 4 МБ flash) для автоматизации теплицы:
полив, форточки на реверсивных приводах, увлажнитель, насос накопительной
ёмкости. Веб-панель на LittleFS, MQTT для Home Assistant, обновление по воздуху.

Язык — C++ (Arduino-фреймворк поверх ESP-IDF), сборка — PlatformIO.
Фронтенд — vanilla JS без сборщика и внешних зависимостей.

---

## Команды

```bash
pio run                  # сборка прошивки + автосборка контейнера OTA
pio run -t buildfs       # сборка образа файловой системы из data/
pio run -t upload        # заливка прошивки по USB
pio run -t uploadfs      # заливка файловой системы по USB
pio run -e ota -t upload # прошивка по сети (заполнить хост и --auth)
pio run -t erase         # стереть флеш целиком, включая настройки Wi-Fi
```

PlatformIO лежит в `%USERPROFILE%\.platformio\penv\Scripts\pio.exe` и в PATH
может отсутствовать.

Полная сборка занимает около двух минут. Если менялся только `data/`,
достаточно `buildfs` — контейнер пересоберётся автоматически.

## Железные факты, которые легко забыть

| Факт | Почему важно |
|---|---|
| `loopTask` работает на **ядре 1**, а не 0 | `CONFIG_ARDUINO_RUNNING_CORE=1`. В коде когда-то было написано обратное |
| AsyncTCP закреплён за **ядром 0** флагом в `platformio.ini` | По умолчанию не закреплён, приоритет 10 — вытеснял управляющий цикл |
| `taskCore1` — приоритет 2, `loopTask` — 1 | Управляющий цикл всегда вытесняет MQTT и OTA |
| Настройки Wi-Fi лежат в NVS `net3` | Не стираются ни прошивкой, ни сбросом к заводским |
| Настройки приложения — NVS `gh5`, одним blob | При изменении `AppSettings` поднимать `APP_SETTINGS_VERSION` |
| Версия прошивки — только `FW_VERSION_MAJOR/MINOR` в `config.h` | Всё остальное читает её оттуда. Не дублировать |
| Разделы: app0/app1 по 1728 КБ, spiffs 576 КБ | Смена таблицы разделов требует первой прошивки по USB |

## Архитектурные правила

### AsyncWebSocket трогать только из задачи AsyncTCP

`std::list<AsyncWebSocketClient> _clients` в ESPAsyncWebServer **не защищён
мьютексом**, а клиенты хранятся по значению. Любой вызов `textAll()`,
`count()` или `cleanupClients()` из другой задачи — это гонка с
`emplace_back()` при подключении и разрушение объекта под работающим
обработчиком при отключении. Так проект ловил перезагрузки раз в несколько
дней.

Поэтому контроллер **ничего не рассылает сам**. Панель раз в секунду шлёт
`{"cmd":"get_state"}`, ответ формируется в обработчике сообщения — то есть
в той же задаче AsyncTCP. Функции `WsHandler::notify*()` намеренно пустые.

### PubSubClient не потокобезопасен

Публиковать можно только из `loopTask`. Внешние вызовы
`MqttMgr::publishRelayState/VentState/PumpState` ставят атомарный бит,
реальная отправка — в `MqttMgr::loop()`. Не добавляйте мьютекс: `doGpio()`
держит `g_settingsMutex` и взял бы MQTT-мьютекс, а `onMqttMessage()` держит
MQTT и берёт `g_settingsMutex` — инверсия порядка блокировок.

### `g_settingsMutex` рекурсивный

Создаётся через `xSemaphoreCreateRecursiveMutex()`, `MutexGuard` использует
`TakeRecursive`. Это осознанно: код изобилует вложенными вызовами вида
«взяли лок → позвали `setRelay()`, который берёт тот же лок». Передавать
в `MutexGuard` обычный мьютекс **нельзя**.

Длинные операции всё же выносите из-под лока: `onModeChanged()` останавливает
моторы и пишет флеш, `settingsSave()` пишет NVS.

### Во время OTA автоматика замирает

`taskCore1` проверяет `OtaMgr::isUpdating()` и пропускает контроллеры,
кнопки и запись истории. Без этого `gracefulShutdown()` останавливал моторы,
а `VentCtrl` через 50 мс запускал их снова; `HistoryLogger` писал бы
в размонтированный LittleFS.

### Реле форточек — только через `setRelayDirect()`

`RelayMgr::setRelay()` для индексов 3–6 **отказывается работать** и пишет
предупреждение. Это защита: парой H-моста управляет `VentCtrl`, который
гарантирует паузы и взаимную блокировку.

## Как проверять работу

Прошивка собирается локально — этим стоит пользоваться вместо рассуждений:

```bash
pio run 2>&1 | grep -E "error:|warning:|RAM:|Flash:"
```

Фронтенд проверяется без железа: скопировать `data/` во временный каталог,
поднять `python -m http.server`, открыть в браузере и подставить состояние
через `renderState({...})`. Так проверялись позиции карточек, цвета кнопок,
адаптивность и переключение языков.

Библиотеки лежат в `.pio/libdeps/` — при сомнениях о поведении
ESPAsyncWebServer или PubSubClient читайте их исходники, а не догадывайтесь.

## Состояние на конец работ по 6.1

**Что сделано:** полный список — в `CHANGELOG.md`, раздел 6.1. Кратко: устранены
причины перезагрузок раз в 3–7 дней, закрыты межзадачные гонки, добавлены
авторизация WebSocket, аварийная точка доступа, калибровочный прогон створок,
управление форточками из Home Assistant, дедупликация записи NVS.

**Что НЕ проверено на железе.** Это главное, что нужно держать в голове:

- Четырёхмесячный аптайм — цель, ради которой чинились гонки, — **не подтверждён**.
  Ни одна из правок стабильности не проверена длительной работой.
- Авторизация WebSocket проверена только на заглушке в браузере, не на контроллере.
- Калибровочный прогон, управление из Home Assistant и аварийная точка доступа
  на живом устройстве не запускались.

Всё перечисленное подтверждено сборкой и локальным тестом фронтенда, не более.
Не описывайте это как «работает» — корректная формулировка «собирается
и проходит локальные проверки».

**На что смотреть в логе после прошивки:**

- `Reset reason:` при старте. Всё, кроме `POWERON`, `SW`, `EXT`, — сбой.
- `[HEALTH]` раз в минуту. `largest` не должен сползать неделями при стабильном
  `heap` — это признак фрагментации. `nvsWr` показывает реальное число записей
  во флеш, по нему решать, нужна ли дальнейшая экономия.
- `[AUTH] 401 ...` — отказ авторизации с указанием URL и причины.
- `[NET] Cache loaded from NVS. SSID="..."` — от этой строки зависит ключевая
  развилка в `setup()`. Пустой SSID означает «уйти в режим точки доступа»;
  непустой — «подключаться к сети». Разбирая жалобу «не поднялась точка
  доступа», смотреть сюда первым делом: она разводит «SSID не стёрся»
  и «стёрся, но AP не поднялась» — а чинится это по-разному.

## Аудит дизайна веб-панели

Проведён отдельно, результат опубликован:
https://claude.ai/code/artifact/95e5f776-671a-4e6b-bc64-1c0ab87a956c

Тринадцать замечаний с измерениями и макетами. Сначала были исправлены только
те, что классифицированы как ошибки («исправь только ошибки, дизайн не меняй»);
позже владелец проекта попросил доделать остальные. **Разобраны все тринадцать.**

Что стоит помнить о последних пяти правках:

- **Цвет часов зависит от фотографии, а не от палитры темы.** Шапка залита
  `banner.jpg`, поэтому `--clock` в каждой теме — светлый и насыщенный, иначе
  цифры пропадут. Брать `--accent` нельзя: в win98 это `#000080`, в skyblue
  `#0d47a1`. Замер по пикселям баннера под часами: фон тёмный (яркость 0.03),
  контраст любой темы не ниже 6.1, у зелёной — ровно как было.
- **Прямые углы в win98 сделаны через `[data-theme="win98"] *` с `!important`.**
  Без него уцелели бы `.input-box input`, `#wifiScanList` и один радиус,
  прописанный инлайном в разметке, — они весят больше. Псевдоэлементы под `*`
  не попадают, поэтому кружок тумблера остался круглым сам собой; индикаторы
  (`.ws-dot`, `.ws-spinner` и прочие) возвращены отдельным правилом.
- **Образцы цветов в плитках тем продублированы литералами.** Показать цвета
  невыбранной темы через `var(--…)` невозможно. При правке палитры в блоках
  `[data-theme]` надо править и `.tsw-*` — сверка делается скриптом из раздела
  «Проверка без железа».
- **Настройки интерфейса живут в двух местах, и это важно.** Тема и язык
  лежат и в NVS контроллера, и в `localStorage` браузера. `localStorage`
  привязан к origin, то есть к IP: сменили адрес — хранилище пустое, и
  панель откроется с языком по умолчанию. Значение из контроллера приходит
  **только** в `/api/settings` и применяется в `fillSettingsForm()` — это
  единственное место, где UI-настройки приезжают с устройства. В снапшоте
  WebSocket блока `ui` нет; ветка, которая его там ждала, удалена как
  мёртвая. Добавляете настройку интерфейса — применяйте её там же и не
  забудьте записать обратно в `localStorage`.
- **Тумблеров в панели шесть, но устроены они по-разному.** Пять — с парой
  подписей, их обслуживает `markToggle()`. Шестой, MQTT, имеет одну подпись,
  и `markToggle` к нему неприменима: слово справа означает связь с брокером,
  а не положение тумблера. Если добавится седьмой — сначала посмотреть,
  сколько у него подписей. Опираться на один только сдвиг цвета нельзя:
  в бежевой и коричневой темах `--text-dim` и `--accent2` почти совпадают
  (`rgb(107,74,0)` против `rgb(92,64,0)`), состояние должно быть словом.
- **Hold-кнопки форточек слушают Space и Enter.** `preventDefault` на `keydown`
  обязателен: гасит прокрутку пробелом и синтетический `click`. Остановка
  висит ещё на `blur`, `visibilitychange` и потере фокуса окном — без этого
  привод шёл бы до `MANUAL_HOLD_TIMEOUT_MS`.

## Проверка без железа

Приём, которым проверялось всё в этой сессии, — воспроизводим:

```bash
# скопировать data/ во временный каталог и поднять сервер
python -m http.server 8777 --bind 127.0.0.1
```

Дальше в браузере через `javascript_tool`:

- `applyLang('ru'); showAppShell();` — открыть панель без контроллера
- `renderState({...})` — подставить снапшот и увидеть реальную отрисовку
- измерения через `getBoundingClientRect()` и `getComputedStyle()` вместо
  скриншотов: точнее и не зависит от рендера панели браузера
- WebSocket проверяется подменой `window.WebSocket` заглушкой, отвечающей
  на `auth` и `get_state`. Не забыть определить `WebSocket.CLOSED = 3` —
  без неё guard в `wsConnect()` блокирует переподключение, и тест врёт.

Так были найдены: горизонтальный скролл на 768–1200 px, одинаковый цвет кнопок
форточек, дубль показаний DHT22 и бесконечный цикл переподключения после
отказа авторизации.

### Три ловушки самой панели предпросмотра

Каждая из них один раз выдала правдоподобный, но ложный результат:

1. **Переходы заморожены.** `getComputedStyle()` вернёт промежуточное или
   стартовое значение. Перед любым замером цвета вставлять
   `*{transition:none!important;animation:none!important}`.
2. **`document.hasFocus() === false`.** `element.focus()` меняет
   `activeElement`, но события `focus`/`blur` не возникают и
   `:focus-visible` не срабатывает никогда. Обработчики проверяются
   синтетическим `dispatchEvent(new FocusEvent('blur'))`, каскад
   `:focus-visible` — временной подменой псевдокласса на класс той же
   весовой категории.
3. **`app.js` кешируется** между `navigate` даже с `force`. Если новая
   функция «не определена» — добавить `?v=N` к URL, а не искать ошибку
   в коде.

## Известные нерешённые вопросы

- **Позиция форточек считается по времени** и дрейфует. Синхронизируется
  калибровочным прогоном (`vent_home`), концевиков в схеме нет.
- **В Home Assistant нет установки позиции форточек** — только OPEN / CLOSE /
  STOP. Механизма «поехать в позицию N» в прошивке не существует.
- **В режиме первоначальной настройки автоматика теплицы стоит.** `setup()`
  уходит в `WifiProv::start()` и возвращается на шаге 8 из шестнадцати:
  `taskCore1` не создаётся вовсе. Пока контроллер ждёт настройки Wi-Fi,
  форточки, полив, увлажнитель и насос не управляются — в том числе не
  закрываются по дождю. Датчики и контроллеры к этому моменту уже
  проинициализированы (шаги 5–6), не хватает только задачи, но менять это
  надо осознанно: `WsHandler`, `OtaMgr` и `HistoryLogger` в этом режиме
  не подняты, а `taskCore1` к ним обращается.
- **Аварийная точка доступа поднимается только при старте.** Потеря сети во
  время работы её не включает.

## Про версию ESP-IDF

Сейчас: `espressif32 @ ~6.9.0` → Arduino core 2.0.17 → ESP-IDF 4.4.7.

Повышение до IDF 5.x требует: перехода на community-форк `pioarduino`
(официальная платформа заморожена на 6.x), переписывания драйвера
ультразвука с legacy `driver/rmt.h` на новый `rmt_rx.h`, правки
`esp_task_wdt_init()` под новую сигнатуру и переименований `sntp_*`.

Смысла в этом сейчас нет: ничего из возможностей 5.x проекту не нужно, а
риск для устройства, управляющего водой, высокий. Возвращаться к вопросу —
если понадобится TLS для MQTT, или при переходе на ESP32-S3/C6.
